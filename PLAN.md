# Finance Tracker — Product & Engineering Plan (v2)

> Goal: an **entry-first personal finance app** with zero sensitive identifiers
> stored, a full ledger of income / expenses / savings / transfers, accounts and
> credit cards tracked by nickname + internal ID, an asset & portfolio register,
> and a dashboard for spending, dues, limits, and net worth.

---

## 1. Product principles

1. **No identifiable account data.** No account numbers, card numbers, CVV,
   expiry, IFSC, UPI IDs, PAN, or PINs — ever. Users type a **nickname** and an
   optional issuer name. The app generates an opaque internal ID (`acc_…`,
   `card_…`) used for all relationships.
2. **Entry first.** Every page leads with a clear way to add something:
   transaction, card, account, asset purchase, asset sale.
3. **Derived balances.** Balances and net worth are computed from the ledger +
   asset register, never typed in and edited later.
4. **Reversible.** Edits are posted as reversals; nothing is silently deleted.
5. **Fast to use.** Defaults, inline creation, duplicate-last, one-screen forms.

## 3. Privacy & data-minimization policy (hard rule)

### Allowed fields
- Nickname ("Salary Account", "HDFC Regalia")
- Kind (savings / current / wallet / cash / brokerage / card / loan; UPI is a payment method tag, not an account)
- Optional issuer/brand text ("HDFC", "ICICI") — a bank name is not a secret
- Currency, opening balance, opening date
- Card metadata: credit limit, statement day, due day
- Internal IDs generated by the app

### Never stored
- Account number, IBAN, card/PAN number, CVV, expiry date, PIN
- IFSC, UPI handle, customer ID, folio number
- Passwords or API secrets in Sheets
- Uploaded statements/documents containing the above

### Enforcement
- `src/utils/privacy.py`
  - `sanitize_free_text(text)` strips long digit runs (12–19), CVV-like
    patterns, and `card number:` style prefixes before persisting.
  - `validate_nickname()` rejects strings that look like account/card numbers.
- UI helper text: *"Use a nickname. Never enter account or card numbers."*
- `Audit` stores only IDs and sanitized descriptions.
- Backups stay in the owner's Drive; `.streamlit/` and `.env` are gitignored;
  the service account has access to the one spreadsheet only.

### `Ledger` (append-only)
| Column | Notes |
|---|---|
| EntryID | `txn_…` (ULID) |
| ClientRequestID | generated when the form is rendered; used for idempotent submit |
| IdempotencyKey | hash of user + type + date + account + amount + normalized description; duplicate detection |
| WriteBatchID | groups every row written by one submit |
| Timestamp | created |
| Date | effective date |
| User | owner |
| Type | `income`, `expense`, `transfer`, `stock_buy`, `stock_sell`, `asset_purchase`, `asset_sale`, `interest`, `dividend`, `fee`, `adjustment` |
| AccountID | affected account |
| CounterAccountID | destination for transfers |
| Amount | paise, positive |
| Fees | paise, optional; capitalized into cost for purchases |
| CategoryID | blank for transfers |
| Description | sanitized |
| Tags | TagIDs (comma-separated), including `method` tags |
| LinkedEntryID | reversal / correction link |
| LinkedTradeID | `InvestmentLedger.TradeID` for `stock_buy` / `stock_sell` |
| DuplicateOfEntryID | set only when the user consciously saves a near-duplicate |
| IsPrivate | |
| Status | `posted`, `pending` (dependent write not yet verified), `reconciled` |
| CreatedBy, UpdatedAt, UpdatedBy | |

**Derived signs** (in `services/ledger.py`):
`income/interest/dividend/stock_sell/asset_sale` → `+AccountID`;
`expense/fee/stock_buy/asset_purchase` → `−AccountID`;
`transfer` → `−AccountID`, `+CounterAccountID`;
`adjustment` → explicit.

**Balance mechanics:**
- A **UPI/bank purchase** debits the selected bank account directly. UPI is a
  **method tag** (`upi`), not a separate account. Only create a `wallet`
  account if it holds its own stored balance (PhonePe/Amazon Pay wallet), in
  which case top-ups are transfers.
- A **card purchase** increases the card's outstanding (expense on the card
  account). No bank account moves until the bill is paid.
- A **card payment** is a **transfer**: `−Amount` from the paying bank account,
  `+Amount` to the card account (reduces outstanding). One row updates both
  balances.
- Balances are derived every time, so there is no separate "update the
  savings balance" step.

| Column | Notes |
|---|---|
| AssetID | `ast_…` (ULID) |
| User | owner |
| AccountID | brokerage/custody account, blank for physical |
| Name | "NIFTY 50 ETF", "Flat 302" |
| AssetType | `equity`, `mutual_fund`, `bond`, `fd`, `ppf`, `crypto`, `real_estate`, `gold`, `vehicle`, `other` |
| Symbol | optional |
| Quantity | derived from `InvestmentLedger` for financial assets; units (1 for property, grams for gold) |
| Unit | grams / sqft / units / etc. |
| AvgCost | paise per unit (fees capitalized), derived from trades |
| CurrentPrice | paise per unit (latest price/valuation) |
| CurrentValue | paise (estimate for physical) |
| ValuationDate | |
| IsActive | |
| LastRebuiltAt | set by the rebuild job |
| DisposedDate, SaleProceeds, RealizedGain | filled on sale |

`Assets` is a **materialized cache**, not the source of truth. For assets with
trade events it is rebuilt from `InvestmentLedger`; a verification job compares
the two. Never edit quantity or average cost by hand — post a trade instead.

### `InvestmentLedger` (append-only holdings ledger — separate from cash ledger)
| Column | Notes |
|---|---|
| TradeID | `trd_…` (ULID) |
| WriteBatchID | same as the linked `Ledger` row |
| Date | trade date |
| User | owner |
| AssetID | `Assets.AssetID` |
| Book | `investment` (equity/MF/ETF/bond/FD/crypto) or `physical` (property/gold/vehicle/other) |
| Side | `buy`, `sell` |
| Quantity | units |
| UnitPrice | paise per unit |
| Fees | paise; capitalized on buys, deducted on sells |
| GrossAmount | quantity × unit price |
| NetAmount | buy: gross + fees; sell: gross − fees |
| AccountID | cash/brokerage account used in the main ledger |
| LedgerEntryID | link to the main `Ledger` cash row |
| RealizedGain | sells only; net proceeds − cost basis |
| Notes | sanitized |
| Status | `posted`, `reversed` |
| ReversalOfTradeID | set on a reversal trade |

**Why two ledgers:** the main `Ledger` answers *where did cash go?*; the
`InvestmentLedger` answers *what did I buy/sell, at what quantity and price?*.
Every stock, mutual-fund or physical-asset purchase/sale writes **both**, linked
by `LinkedTradeID` / `LedgerEntryID`. The investment subset is
`Book = investment`; future charts, allocation and exit analysis read that
subset, so adding those mechanisms never requires changing the cash ledger.
All capital movements (`stock_buy`, `stock_sell`, `asset_purchase`,
`asset_sale`) are excluded from expense and savings-rate KPIs.

### `AssetPrices` (time series — future analytics)
`AssetID`, `Date`, `PricePerUnit`, `Source` (`manual` / `api`), `UpdatedAt`.
One row per asset per day/valuation. Powers "funds over time", portfolio
balancing and exit analysis without touching the cash ledger.

### `PortfolioSnapshots` (derived, cached)
`Date`, `User`, `AssetID`, `Quantity`, `Price`, `Value`, `CostBasis`,
`UnrealizedGain`. Built from `InvestmentLedger` + `AssetPrices`; makes charts
fast and auditable. Rebuildable at any time.

### `AllocationTargets` (future, portfolio balancing)
`User`, `AssetType` or `AssetID`, `TargetPct`, `DriftBandPct`. Read-only input
for future rebalancing suggestions; no ledger effect.

### `Valuations`
`Date`, `User`, `CashTotal`, `LiabilityTotal`, `AssetValue`, `NetWorth` —
monthly snapshots for the net-worth trend.

| IsActive | |

## 4a. Write path, duplication guard & source-of-truth lists

### 4a.1 Exactly what one submit writes

| Entry | Rows written |
|---|---|
| Expense | `Ledger` ×1 (`expense`, status `posted`) |
| Income | `Ledger` ×1 (`income`) |
| Transfer | `Ledger` ×1 (`transfer`: `AccountID` = from, `CounterAccountID` = to) |
| Card payment | `Ledger` ×1 (`transfer`: bank → card) |
| New account / card | `Accounts` ×1 |
| Stock / MF purchase | `Ledger` ×1 (`stock_buy`) + `InvestmentLedger` ×1 (`buy`) + `Assets` upsert |
| Stock / MF sale | `Ledger` ×1 (`stock_sell`) + `InvestmentLedger` ×1 (`sell`) + `Assets` upsert |
| Physical asset purchase | `Ledger` ×1 (`asset_purchase`) + `InvestmentLedger` ×1 (`buy`, `Book=physical`) + `Assets` insert/upsert |
| Physical asset sale | `Ledger` ×1 (`asset_sale`) + `InvestmentLedger` ×1 (`sell`, `Book=physical`) + `Assets` upsert (quantity, proceeds, realized gain) |
| Reconcile | `Ledger` ×1 (`adjustment`) + `Audit` ×1 |
| Set limit | `Limits` ×1 |
| Recurring bill | `RecurringRules` ×1 |
| Payment default | `PaymentDefaults` ×1 |
| Reverse entry | mirror `Ledger` ×1 (+ mirror `InvestmentLedger` row for trades) |
| New category / tag | `Categories` / `Tags` ×1 |

Every row in one submit shares a **`WriteBatchID`**. The main `Ledger` row and
its `InvestmentLedger` row reference each other (`LinkedTradeID` /
`LedgerEntryID`).

### 4a.2 Write sequence (all entry types)

1. **Form render:** generate `ClientRequestID`; prefill defaults (today,
   `PaymentDefaults`, last category, last card).
2. **Validate:** amount > 0, date rule, active account, matching category type,
   ≤ 8 tags, nickname/free-text sanitized.
3. **Duplicate check:** query recent candidates (see 4a.3); show warning or
   proceed.
4. **Generate IDs:** `txn_…`, `trd_…`, `ast_…` (ULIDs) and one `WriteBatchID`.
5. **Build all rows** with `Timestamp`, `CreatedBy`, `Status` (`pending` until
   verified).
6. **Batched write:** append the ledger/trade rows and update the `Assets`
   cache in one service-level batch (gspread may split this into an append plus
   an update; the `WriteBatchID` + read-back make partial writes detectable).
7. **Read back and verify:** every ID exists exactly once; linked rows match;
   then flip `Status` to `posted` and invalidate caches.
8. **Side effects:** update `PaymentDefaults.LastUsedAccountID`, write `Audit`,
   write `NotificationLog` if an alert was shown, `st.toast` success.
9. **New `ClientRequestID`** for the next entry so the same form cannot resubmit.

**Failure handling:** if a dependent write fails, the batch stays `pending` and
is excluded from balances; the UI shows "Needs attention" with an idempotent
**Retry finalize** action. If the sheet was partially written, a reconciliation
job finds rows by `WriteBatchID`, completes them or posts a reversal. Nothing is
silently deleted.

**Immutability:** financial fields are never edited after append. Only
`Status`/`UpdatedAt` may change during finalize; corrections are reversals.

### 4a.3 Duplication protection

Two different problems, handled differently:

**A. Double submit / retry (hard block).**
`ClientRequestID` is unique per rendered form. If a row with the same
`ClientRequestID` already exists, the app returns that entry instead of writing
a second one. The submit button is disabled while writing. This covers
double-clicks, refresh-resubmits and retries.

**B. Same or almost-same entry (soft warning, never silent).**
Before writing, `services/duplicates.py` fetches candidates from a recent window
(default 45 days) and scores them:

| Entry | Candidate match | Warn when |
|---|---|---|
| Expense / income | same user, type, account; date ±2 days; amount exact or within 2%; description similarity ≥ 85 | any candidate |
| Transfer / card payment | same from + to; date ±1 day; amount exact | any candidate |
| Stock / MF trade | same asset, side; date ±1 day; quantity and price equal or within 1% | any candidate |
| Recurring bill vs posted entry | same account/category; due date ±3 days; amount within 5% | offer "mark as paid" |

Description similarity uses `rapidfuzz` (`token_set_ratio`) on sanitized,
lowercased text. Empty descriptions fall back to amount + date + account.
Candidate lookup uses a cached recent-ledger index (date-bounded), not a full
sheet scan; the cache is refreshed after each write.

The warning panel shows the candidate(s) side by side: date, amount, account,
description, tags. Actions: **Cancel**, **View existing**, or **Save anyway**.
Saving anyway writes `DuplicateOfEntryID` and an `Audit` action
`duplicate_override`; the user may add a short reason. The override is auditable
but never blocks legitimate repeat purchases (two coffees on the same day).

**C. Other duplicates.**
- New account/card: normalize nickname + kind + institution; a duplicate
  nickname is rejected, a similar one warns.
- New asset: same normalized symbol/type (financial) or name/type (physical);
  offer "add to existing holding" instead of creating a second asset.
- Recurring bill: same name + account + amount; warn.
- Reversed entries are excluded from candidate matching.

**D. Concurrency.** Google Sheets has no unique index. The service re-reads the
candidate window immediately before append and verifies the `ClientRequestID`
after append. Two truly simultaneous writes are caught by the read-back check
and the later row is reversed automatically. A Postgres adapter later adds a
real unique constraint on `ClientRequestID` and `IdempotencyKey`.

### 4a.4 Where the dropdown lists live

| Dropdown | Source of truth | Rule |
|---|---|---|
| Bank / cash / wallet accounts | `Accounts` where `Kind` in (`savings`, `current`, `wallet`, `cash`, `brokerage`) and `IsActive` | label `Nickname — Kind`; value `AccountID` |
| Cards | `Accounts` where `Kind = credit_card` and `IsActive` | same tab, filtered; caption shows outstanding/available |
| Payment defaults | `PaymentDefaults` → points to `AccountID` | prefill only; resolved account always shown |
| Categories | `Categories` filtered by entry type | inline "＋ New category" |
| Tags | `Tags` + `TagRules` + `lexicon.yaml` | editable chips |

Dropdowns are **not** a separate list or hardcoded config. They are queried from
`Accounts` through `services/accounts.py`, cached in `st.cache_data` for 60
seconds and invalidated after any account write. Archived accounts disappear
from new-entry dropdowns but historical ledger rows still resolve them by ID.
No account number, card number or UPI ID is ever part of an option label.

### 4a.5 Keeping the two ledgers consistent

- Every `stock_buy`/`stock_sell`/`asset_purchase`/`asset_sale` `Ledger` row
  must have exactly one `InvestmentLedger` row, and vice versa. A daily check
  reports orphans.
- `Assets.Quantity` and `AvgCost` are rebuilt from `InvestmentLedger`; manual
  edits are disabled.
- `PortfolioSnapshots` and `AssetPrices` never affect cash balances; they only
  power portfolio analytics.
- Cash KPIs read only the main `Ledger`. Portfolio KPIs read
  `InvestmentLedger` + `Assets` + `AssetPrices`. Net worth joins the two:
  `cash balances + asset current values − liabilities`.

## 5. Entry experience (the core UX)

Use the modern Streamlit toolkit (`st.navigation` + `st.Page`, `st.dialog`,
`st.segmented_control`/`st.pills`, `st.form`, `st.toast`, `st.status`,

### 5.1 Structure

  Bills & Reminders · Limits & Budgets · Settings.
- **Add page:** segmented control across entry types, each in its own
  `st.form` with inline "＋ New account/category" expanders.
- **Quick add:** a `st.dialog` reachable from the dashboard ("＋ Add").
- **Inline feedback:** `st.toast` on success, `st.status` for multi-step writes
  (e.g. stock purchase updates both the ledger and the asset register).

### 5.2 Entry catalog

| Entry | Required inputs | What it writes |
|---|---|---|
| **Expense** | date, account, amount, description → suggested tags/category, private | `Ledger(expense)` → −account, `TagIDs` stored |
| **Income** | date, account, amount, category/source, note | `Ledger(income)` → +account |
| **Transfer** | date, from, to, amount, note | `Ledger(transfer)` → both sides; excluded from income/expense KPIs |
| **New credit card** | nickname, issuer (optional), limit, statement day, due day, opening outstanding | `Accounts(kind=credit_card)` |
| **New account** | nickname, kind, issuer (optional), opening balance, opening date | `Accounts(...)` |
| **Stock / MF purchase** | date, cash or brokerage account, asset name/type, symbol, quantity, unit price, fees | `Ledger(stock_buy)` cash row + `InvestmentLedger(buy)` trade row + upsert `Assets`; fees capitalized |
| **Stock / MF sale** | date, holding, quantity sold, proceeds, fees, receiving account | `Ledger(stock_sell)` cash row + `InvestmentLedger(sell)` + reduce `Assets`, record realized gain |
| **Asset purchase (e.g. house)** | date, asset type/name, quantity/unit, price, fees, paid-from | `Ledger(asset_purchase)` + `InvestmentLedger(buy, physical)` + create `Assets`; fees capitalized |
| **Asset sale (physical)** | date, asset, quantity sold, proceeds, fees, receiving account | `Ledger(asset_sale)` + `InvestmentLedger(sell, physical)` + reduce/dispose `Assets`, record realized gain |
| **Card payment** | date, source account (defaulted), card, amount, method | `Ledger(transfer)` → bank −, card outstanding − |
| **Reconcile** | account, actual balance, date, required reason | `Ledger(adjustment)` + audit |
| **Recurring bill** | name, amount, account, category, frequency, next due, notify | `RecurringRules(...)` |
| **Set limit** | scope, target, period, amount, warn % | `Limits(...)` |
| **Set payment default** | method, default account | `PaymentDefaults(...)` |

### 5.3 Friction removers
- Default to today, last-used account, last-used category.
- **Payment defaults** prefill the source account per method (UPI/card bill),
  but the resolved account is always visible.
- **Confirmation summary** before write: date, amount, source → destination,
  method, category/tags, private. Confirm/Cancel.
- Amount field first on mobile; numeric keypad.
- "Duplicate last entry".
- Draft persisted in `session_state` so a refresh doesn't lose typing.
- Bulk CSV import with `st.data_editor` preview + duplicate detection
  (optional Phase 5).
- Every submit validates before write and shows a plain-language error.

## 6. Dashboard specification

Ordered top to bottom, responsive, with a global filter bar (user, date range,
account, category).

### 6.1 KPI row
Income · Expenses · Net savings · Savings rate. Second row (toggleable):
Net worth · Total assets · Total liabilities · Invested value.

### 6.2 Cash flow & categories
- Monthly income vs expense bars.
- Expense donut by category.
- Category trend lines; savings-rate trend.
- **Tag insights (month filter):** per-tag count, total amount and average;
  merchant comparison (Swiggy Instamart vs Blinkit); parent rollups
  (`fruits` = apples + bananas); item frequency (`chicken`); online vs
  instore split; payment method split (UPI/card/cash); tag filters on the
  ledger.

### 6.3 Cards & dues panel (explicit requirement)
Per card: nickname, issuer, **outstanding**, **available limit**,
**utilization % bar**, **due date countdown**, status chip
(`OK` / `Due in 3 days` / `Overdue` / `High usage`).
Alert rules come from `Settings`:
- due within `N` days (default 7)
- utilization above `warn %` (default 30%, then 50%, 80%)
- available limit below a personal floor

### 6.4 Spending limits panel (explicit requirement)
- Overall monthly limit progress.
- Per-category budgets: spent / limit / remaining, with 80% and 100% warnings.
- Per-card monthly cap (optional) to keep utilization healthy.
- Overspend list at the top of the dashboard as dismissible banners.

### 6.5 Portfolio & net worth
- Asset allocation (financial vs physical, by type).
- Total invested vs current value; top gainers/losers; realized gains YTD.
- **Funds over time:** value chart from `PortfolioSnapshots` (derived from
  `InvestmentLedger` + `AssetPrices`), separate from the cash-flow chart.
- **Future:** portfolio-balancing suggestions from `AllocationTargets` and
  exit analysis from price history — read-only, never auto-trade.
- Net-worth trend from `Valuations` snapshots.
- Upcoming recurring bills.
- Recent entries with one-click reverse.

### 6.6 Alerts engine
`services/alerts.py` + `services/notifications.py` compute deterministic alerts
from `Limits`, `Settings`, `RecurringRules`, card metadata, and the ledger:

| Alert | Source |
|---|---|
| Card due soon / overdue | card due day + outstanding |
| Statement generated (only if statement day set) | optional statement day |
| Card utilization high / low available limit | outstanding vs limit |
| Budget breach / approaching limit | `Limits` |
| Recurring bill due | `RecurringRules.NextDueDate` |
| Pending entries older than N days | ledger `Status = pending` |
| Account not reconciled for N days | last `adjustment`/reconcile date |

Shown as dashboard banners plus a "Pending items" panel computed on page load.
No ML, no background jobs required for in-app alerts. Optional daily email
digest is described in §6.8; `NotificationLog` prevents duplicate sends.

### 6.7 Empty states
Every panel has a short empty state with a call-to-action button that opens the
right entry form (e.g. "Add your first account").

### 6.8 Daily notifications (in-app + optional email)
- **In-app:** computed on every page load from `RecurringRules`, card metadata,
  pending ledger rows and `Limits`. Nothing to schedule.
- **Email digest (optional, Phase 6):** a Google Apps Script time-driven trigger
  (free, daily, reads the Sheet) or a GitHub Actions cron job sends one email
  per user per day. Opt-in via `Settings.notification_email`; the digest lists
  due bills, card dues, budget warnings and pending items.
- `NotificationLog` records `(User, Type, RecordID, Channel)` per day so neither
  channel sends the same alert twice.
- Statement day is optional: if blank, statement alerts are skipped; due-day
  alerts still work.

## 12. Definition of done

- No account/card identifiers are stored; IDs are internal and opaque.
- Every financial movement is a ledger entry with stable account and category
  IDs; transfers do not distort income/expense.
- UPI is a payment-method tag that debits the linked bank account directly;
  cards and loans are liabilities with derived outstanding.
- A double submit writes exactly one row (`ClientRequestID`); a same-or-similar
  entry shows a side-by-side candidate warning and can only be saved with an
  audited override.
- Account/card dropdowns read live from `Accounts`; no separate hardcoded list
  or identifier is stored.
- Stock/MF/ETF and physical-asset trades live in the append-only
  `InvestmentLedger` (`Book` distinguishes investment vs physical), linked to
  the main `Ledger` cash row; `Assets` is rebuildable from trades and verified
  against the cash ledger.
- Investment cash movements are capital movements, not operating expenses;
  portfolio charts, allocation and future exit analysis read the investment
  side without polluting cash KPIs.
- Payment defaults prefill the source for UPI/card bills, but every entry shows
  a final Confirm/Cancel summary before writing.
- A card payment is one transfer that reduces the source balance and the card
  outstanding together; partial payments work.
- Cards show outstanding, available limit, utilization, and due dates with
  alerts; personalized limits warn at 80% and 100%.
- Statement day is optional; due-day alerts work without it. Daily in-app alerts
  cover due bills, pending entries, budget thresholds and low limits.
- Recurring bills are in the upcoming list and alert feed; no auto-posting in
  v1, and `NotificationLog` prevents duplicate alerts.
- An expense description yields editable item / merchant / service / channel /
  method tags and a suggested category; confirmed choices are learned and reused.
- Tag analytics answer count and amount by merchant (`Swiggy vs Blinkit`),
  parent item (`fruits`), specific item (`chicken`) and payment method for a
  chosen month.
- Stock/MF purchases and sales use `stock_buy`/`stock_sell`; physical asset
  purchases and sales use `asset_purchase`/`asset_sale`; fees are capitalized
  and partial sales are supported.
- Assets (stocks, property, gold, etc.) are registered, valued, and sold with
  realized gains; net worth reconciles.
- Income TDS is information-only in v1; tax assist is future and suggestion-only.
- Existing v1 data is migrated and verified.
- Tests cover ledger math, defaults/confirmation, limits, recurring reminders,
  notification dedupe, privacy sanitization, and migration.
